# Controlled changes

`ChangeControl` owns preview, gates, approval, hash-bound permits, apply, status and recovery for a workspace. The product creates one instance per AgentSession and injects it into local edit/write/refactor definitions. SDK factories may inject the same instance using tool options; custom/remote operations are refused when a broker is supplied.

- `changeset.ts`, `patch-plan.ts`, `workspace-edit.ts`: exact after bytes, base hashes and reviewable diffs; initial server resource operations are refused.
- `executor.ts`, `process-lock.ts`, existing file mutation queue: shared locks, journal, durable replacement and precise recovery. Multiple-file atomic visibility is not promised.
- `service.ts`, `approval.ts`: gates and browser confirmation for policy-classified high-risk changes. No UI means required approval is refused.
- `factory.ts`, `change-store.ts`: private agent-directory persistence, shared across sessions/processes of that directory.

`preview_server_refactor` requests an exact unique enabled edit-only formal LSP refactor (including edit resolution) through the existing synchronized backend and previews its WorkspaceEdit through this same broker. Command/interactive actions are refused before resolution/execution; no arbitrary executeCommand is enabled. Mock planning and shared-executor conflict/apply tests pass; a real TypeScript command action was refused without writes, not counted as successful refactor acceptance. Compiler signature/API adapters and a real edit-only compilation acceptance remain unfinished.

`previewWrite` deliberately preserves full-write semantics (UTF-8 content replaces the whole file), while edit and LSP plans preserve original encoding/line endings. Changed base hashes invalidate a plan.

## Unfinished quality enforcement

The code-intelligence runtime supplies a TS/JS structural-reuse gate to each session broker using the same CodeSymbolIndex. It checks actual proposed bytes, including token blocks copied into existing functions, same-file duplicates and duplicates created together in one changeset. It uses a workspace/managed compiler, not a product dev-only compiler. Matching 32-token windows are review candidates, not proof of behavioral equivalence. Unsupported language/compiler/index budgets remain unknown (strict gate refuses unknown; assist allows unknown). Complete TS/JS structural candidates now support explicit host-user exceptions through the existing ApprovalPort, never policy/model approval. The user is asked to compare source and contracts and decide why reuse is unsuitable. Review collects all structural candidate path groups (up to 100, exceeding that blocks) rather than approving only the first hit. Exceptions bind actual scanned source/config hashes, compiler version, inventory and exact preview, expire with the permit TTL, are rechecked both immediately and after other gates/risk approval, and persist as user-approved gate evidence. Missing UI, refusal, cancellation, incomplete coverage or changed snapshots cannot authorize an exception. Approval is per apply attempt, not a reusable bypass. Intent/signature/behavior candidate retrieval and structured contract comparison remain unimplemented. Preview-bound root/impact reviews are available through refactor review_impact and required by strict apply. They require exact modified-path accounting, root-cause evidence, compatibility and check declarations. Apply also compares the actual stored plan against the plan supplied to its gates before and after approval; interleaved plan changes require a fresh review rather than authorizing old graph evidence. Local root/affected evidence files (including unchanged callers) are hash-bound, validated for missing paths/stale preview bases, and rechecked before and after approval. Legacy declaration-only reviews remain readable but cannot authorize strict writes. The product runtime now also queries semantic declarations and references for roots and existing modified files in strict mode, and uses the existing same-object inspection for applicable call, implementation and type relations (including paging). It also searches the shared index for lexical/string candidates by declaration name and requires separate affected-path decisions; these are explicitly not semantic references. It refuses omitted local consumers/candidates or incomplete queries. Only outside-workspace relation warnings with exact external-file decisions are accepted; other partial results block writes. It checks the indexed workspace before/after querying. Queries honor cancellation and run again after approval before a permit is created. Successful query receipts persist privately under `gate-evidence/`, bound to the preview's base/after hashes, review hash and indexed workspace snapshot; they contain actual query metadata and relation pages, not model-supplied query claims. This gate is shared by edit/write/refactor; assist/off do not trigger it. Dedicated configuration/data and newly created declaration adapters, full override/alias/reverse-project coverage, dynamic registration, independently verified external consumer decisions and fully atomic approval-to-execution evidence freshness remain missing. Declared completeness and reference coverage do not prove business root-cause correctness. SDK brokers without runtime gates do not gain this query enforcement automatically. Session now attaches `ChangeVerification`: configured checks establish a baseline, committed changes retain disk-backed verification debt, and completion checks the current workspace snapshot before reporting success. Missing checks or coverage stay unknown; failures after a passing baseline allow at most three path-scoped repair rounds. In assist mode, automatic completion enforcement requires explicit verification enablement or configured checks; an unconfigured default does not block ordinary conversations. Strict mode still requires verification unless explicitly disabled. Automatic completion/repair covers only the current user task; continuation rounds retain its scope. Historical debt remains available to explicit workspace status/verify and cannot block unrelated chat or expand repair permission. Skipping automatic enforcement does not clear debt or mark changes verified. The original task baseline is retained while its changes need verification; each check run copies its configuration and persists the exact checks hash that passed. Enablement or repair-budget changes during a run also invalidate its result as unknown; passing exit codes cannot certify checks under a changed policy. Baseline/check persistence and verification runs reuse the store's cross-process lock, preventing independent service instances from overwriting a newer result with an older run; status reads and multi-record crash atomicity remain limited. Cancellation cannot produce verified success, and automatic repair refuses writes after check configuration, enablement or repair-budget changes; pre-change checks receive the operation cancellation signal. Automatic repair refuses test, check-configuration, dependency and policy paths even within the original file scope; changing those requires separate user review rather than weakening the check. `refactor verify` runs the same service. Settings expose off/assist/strict; strict denies unbrokered Agent tools but is not an OS sandbox. Diagnostic-level old-error attribution, complete business impact proof and language-specific automatic check discovery remain unimplemented. Diagnostic queries re-read their target on disk before returning; an externally changed target produces partial stale coverage rather than certifying the old answer. Product refactor preview refuses partial/nonsemantic rename proposals before persisting a preview, while preserving expected-name ambiguity errors. This prevents known omitted-consumer results (including managed Shell) from becoming policy-approved rename writes. Complete metadata alone remains insufficient proof of all consumers. `committed` means only that the controlled write committed, not `verified`. Shell/custom tools are not isolated by these locks, and external user edits cannot be prevented. Do not enable applyEdit capability or advertise absolute write interception based on this module alone.

Tests live in `test/changes/`, `test/file-mutation-queue-multi.test.ts`, `test/refactor-tool.test.ts` and `test/code-intelligence/real/refactor-rename.real.test.ts`. Real server tests are separate from protocol fixtures.
