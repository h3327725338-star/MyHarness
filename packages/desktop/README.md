# MyHarness Electron desktop (Windows x64)

This private workspace hosts the existing Web application; it is not another frontend or Agent runtime.

## Commands

From the repository root:

```powershell
npm.cmd install --ignore-scripts
npm.cmd exec -w @myharness/desktop -- install-electron
npm.cmd run desktop:dev
npm.cmd run desktop:pack
npm.cmd run desktop:test
```

**Double-click launcher (daily development)**: `dev-desktop.cmd` in the repository root builds, packages and then starts the newest build in one step (`packages/desktop/pack-and-run.ps1`). It shows real progress in its window and closes on success; on failure the window stays open with the error. Before starting it closes a running MyHarness, because the single-instance lock would otherwise make the new build exit immediately and silently leave the old window in place. It resolves Node/npm itself (PATH first, then the usual install locations), so a double-click from Explorer also works when that inherited PATH has no Node.

Artifacts of this launcher land in `dist\desktop` (it pins `MYHARNESS_DESKTOP_OUTPUT`, so an inherited `MYHARNESS_ARTIFACTS_DIR` cannot move them into a conversation folder). After a successful build it deletes older `stage-*` directories and keeps only the newest two `release-*` directories; anything that cannot be deleted (for example a still running build) is reported and skipped. `MYHARNESS_DESKTOP_SKIP_LAUNCH=1` builds without closing or starting anything.

`desktop:pack` runs the unchanged root build, stages only compiled MyHarness packages, Web resources, system prompts and their installed runtime dependency closure, then uses electron-builder to create `win-unpacked/MyHarness.exe`. Keep the entire `win-unpacked` directory together. No external Node, tsx or npm is needed to start it. Bash/Git and optional tools still have the same requirements as the Web product; this does not bundle a development toolchain.

Output goes to `MYHARNESS_DESKTOP_OUTPUT`, otherwise the current conversation's `MYHARNESS_ARTIFACTS_DIR/desktop`, otherwise root `dist/desktop`. Each build uses a new timestamped staging/release directory; `build.mjs` itself never deletes previous builds (only `pack-and-run.ps1` prunes old ones as described above). Electron download failures must be resolved using the actual installer error; no alternative shell is used.

## Startup, storage and lifetime

`MyHarness.exe → Electron main → Electron exe with ELECTRON_RUN_AS_NODE=1 → service-entry.cjs → existing coding-agent dist/web.js → main/startWebBootstrap → HTTP/SSE → existing web/`.

Development uses that same chain with `packages/coding-agent/src/web.ts` and the repository dev loader. Refresh for frontend changes; close/relaunch for backend changes. The browser launch scripts (`dev-web.cmd` and its helpers) have been removed: the desktop app is the way to use MyHarness, and `node --import ./scripts/dev-fast-loader.mjs ./packages/coding-agent/src/web.ts` runs the sources from a command line without opening a browser.

The source host anchors its working directory to the repository. The packaged host records that directory in `runtime.json` at build time, independently of where the executable is copied. This is intentional for this checkout's desktop/Web shared-data requirement: Agent configuration remains in `~/.myharness/agent` (or the existing environment override); current Session/Workspace data remains in the checkout's `data/`, not a new Electron data store. `MYHARNESS_DESKTOP_CWD` can explicitly select a different working directory; `MYHARNESS_DATA_ROOT` retains the backend's existing semantics. A different machine needs an explicitly chosen existing working directory; a build-time checkout path is not a universal installer data location.

Only Chromium host/third-party profile data is added under the Agent directory's `desktop-profile`. Third-party views use the separate persistent `myharness-third-party` partition, never the system browser profile. Web UI appearance preferences (theme, language, motion, widths, panel tab, run mode, notifications) are kept by the service in the Agent directory's `web-ui-prefs.json` and shared with the browser Web UI (see `packages/coding-agent/docs/web-ui.md`), so the per-start random port no longer resets them. Earlier desktop builds kept them only in the localStorage of each start's origin; on start, when the service has no shared preferences yet, `legacy-prefs.cjs` reads those copies from this profile's LocalStorage log (read-only) and moves the user's last choice of each preference there once. When copies exist but none can be read, the page starts with defaults and says so. Server settings and persisted conversations use the same backend paths.

The service listens on port 0 and reports the actual loopback address. A process waits for IPC before initializing, so the main process can first assign it to a Windows kill-on-close Job Object (Koffi calls Windows APIs). Descendant shells, PTYs and tasks inherit ownership. Window close requests existing graceful shutdown, waits up to eight seconds, then closes the job. The existing restart route retains its work checks and disposal, but desktop restarts are supervised over IPC rather than detached PowerShell. Single-instance locking activates the existing window.

Logs append to the existing data root's `logs/web-launch.out.log` and `web-launch.err.log`. Service/load failures produce a Chinese error page. No Agent data or credentials are copied into the distribution.

A click on the task-end notification is a Windows activation: it starts whatever the Start Menu shortcut carrying the app's AppUserModelId points at, which may be a new process rather than the running window. The id therefore has to name one launcher that starts this app. The packaged build keeps `MyHarness`; a source run of `electron.exe` uses `MyHarness.Dev`, because Electron always writes that shortcut without the app path and would otherwise compete for the installed app's notifications with a shortcut that starts Electron's default window. On start the packaged build also removes Start Menu shortcuts that still claim `MyHarness` without being able to start this app (a leftover of a source run, or a build folder whose executable is gone); Electron writes its own shortcut again before the next notification, and a shortcut of another installation that still exists is kept, because starting it forwards to the running window through the single-instance lock.

## Window frame

The window has no system title bar (`frame: false`); the Web UI's own top row is the title bar. Its empty parts (the conversation header, the workspace panel head and tab strip, the sidebar's brand row) are `-webkit-app-region: drag`, so moving the window, double-click to maximize/restore, Aero Snap and drag-to-restore from maximized are handled natively by Windows; every control inside them is `no-drag`, and so are dialogs, menus and the column resizers that overlap them (`web/css/layout.css`, end of file). The edges and corners keep the native resize borders, and a maximized window fills the work area without covering the taskbar.

In the desktop window the columns fill the window edge to edge (no outer gap or rounded corners against the frame, a 1px line between columns), and the conversation header and the workspace panel head are the same height, so their bottom lines meet. Minimize, maximize/restore and close are drawn by the page (`web/js/window-controls.js`, existing `.icon-btn` and design tokens) as Windows-sized blocks (46px wide, the top row's 44px high) flush in the window's top-right corner: in a maximized window the corner pixel is the close button, and a restored window keeps the native resize corner on its outermost pixels. They sit on whichever top bar ends at the right edge: the conversation header, or the workspace panel head while the panel is the right-hand column. They call `myHarnessDesktop.windowControls` (`desktop:window` IPC: `minimize`, `toggleMaximize`, `close`, `state`), and main reports every maximize/restore/fullscreen change (`desktop:window-state`), so the button follows Snap, Win+Up/Down, the taskbar and double-clicks too. Close takes the same path as the system close (Alt+F4, the taskbar), which follows Settings → Appearance → Desktop app → "Close button" (`app-prefs.cjs`, `desktop-prefs.json` in the host profile): until the user chooses, the page asks in its own dialog (workspace command `askClose`, `CloseAppModal` in `web/js/app.js`; the window is shown first) whether to minimize to the system tray or quit, with "remember my choice" — a page that cannot answer (crashed, reloading) leaves the question to a native dialog; minimize to tray hides the window and keeps the local service and running tasks alive (the tray icon shows the window again, its menu quits), quit hides the window and stops the local service. While the host's own starting/error page is shown, and on Windows sign-out, close always quits. "Start with Windows" on the same card writes the Windows Run entry through `app.setLoginItemSettings` (read back from Windows each time, never cached); a start at sign-in carries `--autostart` and shows the window without taking the focus. The page reaches both through `myHarnessDesktop.appPrefs` (`desktop:app-prefs` IPC, app page only). The starting and the error page that main shows itself carry the same three buttons and a drag strip; the IPC check accepts the app page (the existing `trusted()` rule, unchanged) or exactly the page main loaded itself, and nothing else. `document.title` still names the window for the taskbar and Alt+Tab.

Windows' Snap Layouts flyout on hovering the maximize button belongs to the native caption buttons and is not shown for these page-drawn buttons; Win+Z and drag-to-edge snapping still work.

## Built-in browser and the workspace

The right-hand panel is one workspace with tabs: the four existing panels (Changes / Files / Terminal / Session) keep their single tab each, and any number of local files (text, code, Markdown, JSON, images, PDF, Office, audio, video) and websites can be open at the same time. The header's globe button opens a website tab. A tab strip at the top of the panel switches between them, closes one (× or middle click), closes the others (right-click menu), restores the most recently closed one, and reorders them by dragging; the open tabs and the active one are saved with the other page preferences, so they come back after a reload. Closing the panel keeps every tab; the panel's state is not thrown away when you close it.

Each website tab is a sandboxed `WebContentsView` without Node integration (its only preload is the sign-in helper described below, in the page's isolated world): a real Chromium document with its own history, not an iframe or webview. Every tab shares one persistent `myharness-third-party` partition, so cookies, localStorage and (when the site stores its login there) login state survive restarts and tab switches; nothing is copied from or written to the system browser profile. Web links that open a new window become workspace tabs; the engine creates the popup's page itself (`createWindow`), so it keeps `window.opener` and popup sign-ins ("Sign in with Google" and the like) can post their result back, and a popup that closes itself (`window.close()`) closes its tab and the tab that opened it comes back. A link in an HTML file shown in a file tab (the sandboxed preview frame) that points to another site never loads inside the frame, where most sites refuse to be framed and the preview went blank (`preview-links.cjs`): the host sends it to the page with `link: true`, and the page opens it as a website tab or in the system browser, following Settings → Appearance → Interface → "Open web links in" (`web/js/link-target.js`); links between the file's own pages still navigate the frame. A new-window link (`target="_blank"`) in the preview or anywhere in the app window goes the same way through the window-open handler in `main.cjs`, falling back to the system browser only when the page does not answer; sign-in links that must use the system browser are opened by the page itself. Downloads are saved with a collision-free name under the system Downloads folder and reported with progress (the host command surface can cancel by id and retry), and a toolbar shield lists site permissions. A permission request (camera, microphone, clipboard, notifications, geolocation, external open, …) is not granted by default: the tab asks with Allow for this session / Deny, an unanswered or abandoned request is denied, the decision is remembered for this app session only, and it can be revoked from the shield. A bookmarked site is the user's own choice of a trusted site: its requests are allowed at once (the tab shows a notice saying so). The Agent sees pending requests in a tab's `state` (`pendingPermissions`) and can allow or deny them with `answer_permission`; such a decision is reported in the tab as the Agent's. A tab sends the engine's own user agent (with its `Electron/x` token) everywhere except on WhatsApp Web and Microsoft Teams (`CHROME_UA_SITES` in `browser-view.cjs`), which get the user agent of a current desktop Chrome (`Chrome/<major>.0.0.0`, without Electron's and the app-name tokens) because they sniff those tokens: with Electron's string WhatsApp Web shows "works with Google Chrome 100+" and Teams loads its desktop-client path and stays blank. Only on those pages does the tab preload add the "Google Chrome" brand to `navigator.userAgentData` and the request headers carry matching client hints. The choice is made per top-level navigation, so one tab can move between such a site and any other. It is not applied everywhere because Cloudflare Turnstile fails ("Verification failed") on any page whose user agent claims Chrome while the engine is Electron; with the engine's own string it passes. The engine itself is unchanged; its real Chromium and Electron versions are shown in the site-permissions card and on an empty tab. The Electron version is pinned exactly in `package.json` and kept on the latest release by `.github/dependabot.yml`; `build.mjs` packages whichever version is installed. This does not promise access to blocked networks or bypass site login, bot checks, DRM or Electron-specific site restrictions.

In-page find (`Ctrl+F` inside the page, the search button, or the Agent's `find` command) uses the real `findInPage`/`found-in-page` result and shows the match count. The file tabs have their own find bar for text files. The Agent can upload one workspace file into a page's `<input type=file>` with `upload`; the desktop host resolves the path inside the current workspace only, requires a regular file, enforces a 100 MiB limit and refuses directories, missing files and paths outside the workspace. Upload progress is not exposed by Chromium's file-input API, and a cancelled upload is a cancelled page-side operation, not a resumable transfer.

A native view is drawn above the whole page and takes no part in its layout, animations or stacking. `web/js/browser-view-sync.js` measures the tab's real box: while the box moves (panel drag, window resize, scrolling) the native bounds follow the measured box; a box that is hidden (animation, dialog, clipping, hidden page, inactive tab) is shown again only after two stable checks, and the view is also hidden while a dialog/popover/toast covers it, a scrolling ancestor clips it, the page is hidden, or the tab is not the active workspace tab. The page calls `hide` before rendering a non-browser tab, the component reports a null rectangle for its own tab when it unmounts, and active/tab/close state is enforced again in the host (`activate` without fresh bounds stays hidden, `close` never promotes another view to the old box). Main clamps bounds to the window and refreshes them on resize/maximize/restore/fullscreen events. Closing a tab cancels its downloads, clears its find/permission callbacks, timeouts and screenshot interval, detaches and closes the view, and drops its network references. The hidden page itself stays alive, so its history, form state and scroll position survive a switch; the fallback picture (`capturePage`, JPEG) is refreshed only while the view is visible. Load failure/45-second timeout leaves a visible message and a system-browser action. The context menu supports editing/copy and opening the page externally. No global keyboard shortcut or window-level fullscreen toggle is implemented. Multi-window OAuth flows are not implemented as a full browser product.

## Saved sign-ins and bookmarks

Both live in this host's user-data folder (the Agent directory's `desktop-profile`), never in the Data root or a
workspace, so Google Drive sync never picks them up and they stay on this computer.

- **Saved sign-ins** (`browser-passwords.cjs`, `browser-tab-preload.cjs`). Each site tab gets a preload that runs in the
  page's isolated world (the site's scripts can neither see nor call it). When a form with a password field is
  submitted (a real submit, a click on a button, or Enter), it reports the user name and password to the host; the
  first step of a two-step sign-in only reports the user name. The host saves the login only after it looked
  successful: the next page has no password field, or on a single-page app the field went away and stayed away. A form
  that is still on screen (wrong password) is not saved. The file `browser-logins.bin.json` is one blob encrypted with
  Electron `safeStorage` (Windows DPAPI, bound to the Windows user): sites, user names and passwords are all unreadable
  in it, and without OS encryption nothing is saved. A file the current Windows user cannot decrypt is never
  overwritten. One entry per site origin and user name; a new password replaces the old one. On the next visit to a
  login page of the same origin the preload asks the host for that origin's logins (the host decides the origin from
  the sending frame, main frame only, http/https only) and fills the user name and password, most recently signed-in
  account first; typing another saved user name fills its password. On its own it never presses the site's button and
  never overwrites what the user typed. The one exception is the Agent's `login` command on a bookmarked site: the host
  asks the tab's helper (`mh-browser:agent-login`) to fill that site's saved login and submit the form the way its own
  button would; the answer names the user name and whether the password field was there (a two-step sign-in is done by
  calling `login` again on the next page), never the password. A site that is not bookmarked, or has no saved login,
  is refused. Logs only name the origin; the workspace page receives site and user name only
  (`passwords` command), never a password. Entries are listed and deleted in the site-permissions card; a deleted entry
  is no longer filled. Limits: a filled password is in the page's input like any typed password, so the site's own
  scripts and the Agent's `exec` command on that tab can read it (Chrome hides autofilled values until a user gesture;
  this host does not). Sign-ins inside sub-frames are neither saved nor filled. The success heuristic can miss a site
  that keeps a password field on its post-login page or hides its form before reporting an error. Electron 45 marks
  the synchronous `safeStorage` calls used here as deprecated (they still work); moving to the async API is open.
- **Bookmarks** (`browser-bookmarks.cjs`): `browser-bookmarks.json`, written atomically. Adding one stores the page's
  icon inline as a data URL (at most 64 KiB, fetched through the tab's partition; Chromium's favicon event, then the
  page's `<link rel=icon>`, then `/favicon.ico`), so the bar works offline; without an icon the bar shows the first
  letter. A damaged file is set aside as `.damaged` before the next write. Commands: `bookmarks`, `bookmark-add`,
  `bookmark-update`, `bookmark-remove`; every change is broadcast as a `bookmarks` status so all tabs agree. `Ctrl+Shift+B`
  in the page is forwarded to toggle the bar. A bookmark also marks its origin as trusted (`bookmarked` command):
  permission requests are allowed at once and the Agent may use `login` there.
- **New-tab shortcuts** (`browser-speed-dial.cjs`): `browser-speed-dial.json`, written atomically, holding the layout of
  the new-tab page: sites and one level of groups, in the user's order (at most 200 sites, http/https only, titles up
  to 80 characters and may be empty for an icon-only shortcut, icons inline up to 96 KiB). Until the first change the page shows the first 12 bookmarks and nothing
  is written. Commands: `speeddial` and `speeddial-save` (the page sends the whole cleaned layout; every change is
  broadcast as a `speeddial` status). After a save the host fetches missing icons in the background through the
  partition (a bookmark of the same origin first, then the site's `<link rel=icon>`, then `/favicon.ico`) and remembers
  a site that has none.

The Agent's workspace tool sends only its own fixed browser actions: it can list bookmarks and use a saved login through
`login`, but it cannot read a saved password, and it cannot add or delete saved sign-ins, bookmarks or shortcuts.

## The Agent's workspace tool

In Electron only, the service process gets a `workspace` tool (`packages/coding-agent/src/tools/workspace.ts`). It is registered only when `MYHARNESS_DESKTOP_HOST=1` and the IPC link is connected, so a plain CLI session never advertises it. Two channels, both request/response with a timeout and a real error on failure:

- **Browser channel** — the service asks the main process over the child-process IPC link; main acts on the addressed `WebContentsView` and answers with the state it reached: `list`, `open`, `ensure`, `activate`, `bounds`, `hide`, `refresh`, `close`, `state`, `navigate`, `back`, `forward`, `reload`, `stop`, `find`/`stopFind` (real match count and active match), `text`, `dom`, `ax` (Chrome accessibility tree), `interactive`, `interactive` (with visibility, on-screen state, current value and checked state per element), `click`/`type`/`locate` (an element by CSS selector, the index from `interactive`, or `label`: its visible words, placeholder or accessible name; it is scrolled into view and pressed with the Agent's real mouse at its centre, falling back to the element's own click() when another element covers that point; `type` clicks the field, selects its text unless `replace: false`, enters the text through `Input.insertText` and only sets the value directly when the page dropped it, picks a `<select>` option by value or label, and presses Enter with `enter`), `wait` (a selector, text or label appearing or, with `gone`, disappearing, or the page loaded with half a second of network quiet; a timeout is an answer, not an error), `mouse` (the Agent's own mouse: click, double click, right click, move, down, up, drag and wheel at a CSS-pixel point, sent as trusted DevTools-protocol input events, with what was under the pointer in the answer and a small pointer drawn in the page's isolated world so the user sees where it acted), `keys` (key names and combinations such as `Control+A`, `browser-input.cjs`), `insertText` (text into the focused element), `login` (saved login on a bookmarked site, see above), `upload` (one workspace file into a page file input), `scroll`, `exec` (page JavaScript), `snapshot` (PNG of any tab, on screen or not, through the page compositor, scaled to the page's CSS pixels so a point in it is a point for `mouse`), `downloads` (finished and running, plus the downloads folder)/`download` (save a link with the tab's own session and wait for the file)/`download-cancel`/`download-retry`; an Agent `mouse` click that starts a download waits for it (up to 6 s to start when the clicked control names a download or a file, 0.4 s otherwise, then up to 30 s to finish) and returns the saved file in its answer, `network` (recent request metadata: method, URL, status, type — no bodies or headers), `permission`/`permissions`/`revokePermission` for the session-scoped site-permission decisions, and `external` (system browser). Download and request logs are capped (50 and 200 entries) and never persisted. Only the app page can call these commands; the website itself never gets the bridge.
- **Workspace channel** — the page owns its tab list and the media elements, so main forwards the command to the page (`desktop:workspace`) and the page answers with the state it reached (`tabs`, `open`, `close`, `activate`, `closeOthers`, `move`, `reopen`, `media` with play/pause/seek/volume/mute/rate/subtitles). A page that does not answer in 15 seconds is an error, not an assumed success.

Both channels are reachable only from the app's own page (same service origin, main frame) through `contextBridge`; the page cannot call raw Electron or Node APIs. Every browser command addresses a tab by id and works whether or not that tab is on screen: a hidden tab gets the viewport the visible tab last had but never less than 1280×800 (set before the view is hidden, because Electron does not pass bounds set on a hidden view to its page), so the Agent can drive several tabs side by side, and `open` with `background: true` adds a tab without switching the user's view. Commands from the service's IPC link are the Agent's (`command(input, { agent: true })`): they keep the tab awake first. The tab on screen always has exactly the panel's size, also while the Agent drives it (no scaled-down desktop picture); mouse points are page CSS pixels. A coordinate click that lands on a plain container next to a control reports `missed` and the `nearest` control's centre in its `target`. Screenshots are written to the session's temporary directory (the tool keeps the newest 50 and deletes older ones) and the picture itself is attached to the tool result, resized for the model when it is large (the result then says how to map back to page coordinates).

## Verification limits

Use actual test reports for evidence. Unit tests and browser module smoke checks do not establish human input, visual alignment at every DPI level, all Git flows, clean-machine compatibility or login compatibility. The workspace and the built-in browser have: unit tests for the command surface, state machine and permission decisions (`test/browser-tabs.test.cjs` with a mocked Electron); unit tests for saved sign-ins and bookmarks (`test/browser-profile.test.cjs`: encrypted file contents, one entry per site and user name, overwrite on a new password, no saving without OS encryption, the success heuristic, origin and sub-frame checks, bookmark persistence and damaged-file handling; a one-off real-Electron run of the same flow against a local login page on this machine is not part of the repository); a real-Chromium test of the page's tab model and workspace commands (`packages/coding-agent/test/web-workspace-tabs-browser.test.ts`); a real-Chromium test of native-view placement, hide-on-tab-switch, in-page find, upload validation and permission UI (`packages/coding-agent/test/web-workspace-browser-view.test.ts`); a real child-process IPC test of the Agent tool with an isolated faux model (`packages/coding-agent/test/workspace-tool-ipc.test.ts`); and a real-Electron harness (`test/electron-browser.e2e.cjs`) that drives the actual `WebContentsView` command surface, downloads, cancel/retry, popups, permission allow/deny/revoke, persistence across a restart, and runs the real `workspace` tool over real IPC against this Electron main process with a faux model. A second real-Electron harness (`test/electron-agent-control.e2e.cjs --profile=<empty dir>`, window never shown) drives hidden tabs with the Agent's mouse and keyboard (canvas and image clicks at exact CSS points, double/right click, drag, wheel, typing, `Control+A`, `Enter`), captures a hidden tab and checks its pixels, checks the pointer overlay never swallows a click, the bookmark permission grant, the Agent answering a pending request, a saved login used by `login` against a local form, tab icons and shortcut icons. A fourth one (`test/electron-popup-preview.e2e.cjs --profile=<empty dir>`, window never shown) checks that a sign-in popup and an about:blank popup keep `window.opener`, report back, close their own tab and leave none behind, that closing the window with a popup tab open raises no main-process error, and that a preview link to another site opens a website tab while the preview keeps its page. A third one (`test/electron-agent-view.e2e.cjs --profile=<empty dir>`, window shown inactive, unfocusable and off-screen, because the scaled view behaves like the app's only when composited) checks the Agent's desktop-size view in a 426 px panel and in a tall 1005 px maximized panel (both filled; full-size screenshot, exact click on a far-right control, the scaled view bounds, a fallback picture of the scaled box), a synthetic person's click handing the page back, a background tab's desktop-size viewport, and a click-started and a direct `download` reporting the saved file. A fifth one (`test/electron-agent-limbs.e2e.cjs --profile=<empty dir>`, window never shown) checks pointing at elements: click by visible text on a control that only answers trusted pointer events, a menu item that appears later (`wait`), a clickable <div> found by its words, a button below the fold, a covered link, typing by placeholder with Enter, replace and append, a field that refuses keyboard input, a <select> by label, a contenteditable, and waits that succeed, disappear and time out. Unit tests with a mocked Electron cover the same commands (`test/browser-agent-control.test.cjs`), the page's shortcut layout rules are in `packages/coding-agent/test/web-browser-speed-dial.test.ts`. Run the harness twice with `npm.cmd exec -w @myharness/desktop -- electron packages/desktop/test/electron-browser.e2e.cjs --phase=1|2 --profile=<dir> --downloads=<dir>`. That harness and the page fixture do not cover the app page's own transport (`contextBridge`/`ipcMain`/`desktop:status`); that path was exercised in this workspace with a one-off CDP driver against the running app at 100 %, 125 % and 150 % display scale, including a real pointer drag, Session/Terminal/file/media switches, maximize/restore while the browser was hidden, and tab close/reopen. That driver is not part of the repository, so its results are evidence for this machine only, not an automated guarantee. No real provider model turn was run; the tool round used the isolated faux model. Office documents remain read-only (download/external open), PDF uses Chromium's bundled viewer (view, zoom, page, search, copy, download), and image zoom/rotate is view-only (no crop, annotation or save). The app is unsigned; Windows SmartScreen policy may warn. No auto-updater or installer is provided by the directory target.
