# MyHarness Electron desktop (Windows x64)

This private workspace hosts the existing Web application; it is not another frontend or Agent runtime.

## Commands

From the repository root:

```powershell
npm.cmd install --ignore-scripts
node node_modules/electron/install.js
npm.cmd run desktop:dev
npm.cmd run desktop:pack
npm.cmd run desktop:test
```

**Double-click launcher (daily development)**: `dev-desktop.cmd` in the repository root builds, packages and then starts the newest build in one step (`packages/desktop/pack-and-run.ps1`). It shows real progress in its window and closes on success; on failure the window stays open with the error. Before starting it closes a running MyHarness, because the single-instance lock would otherwise make the new build exit immediately and silently leave the old window in place. It resolves Node/npm itself (PATH first, then the usual install locations), so a double-click from Explorer also works when that inherited PATH has no Node.

Artifacts of this launcher land in `dist\desktop` (it pins `MYHARNESS_DESKTOP_OUTPUT`, so an inherited `MYHARNESS_ARTIFACTS_DIR` cannot move them into a conversation folder). After a successful build it deletes older `stage-*` directories and keeps only the newest two `release-*` directories; anything that cannot be deleted (for example a still running build) is reported and skipped. `MYHARNESS_DESKTOP_SKIP_LAUNCH=1` builds without closing or starting anything.

`desktop:pack` runs the unchanged root build, stages only compiled MyHarness packages, Web resources, system prompts and their installed runtime dependency closure, then uses electron-builder to create `win-unpacked/MyHarness.exe`. Keep the entire `win-unpacked` directory together. No external Node, tsx or npm is needed to start it. Bash/Git and optional tools still have the same requirements as the Web product; this does not bundle a development toolchain.

Output goes to `MYHARNESS_DESKTOP_OUTPUT`, otherwise the current conversation's `MYHARNESS_ARTIFACTS_DIR/desktop`, otherwise root `dist/desktop`. Each build uses a new timestamped staging/release directory; `build.mjs` itself never deletes previous builds (only `pack-and-run.ps1` prunes old ones as described above). Electron download failures must be resolved using the actual installer error; no alternative shell is used.

## Startup, storage and lifetime

`MyHarness.exe → Electron main → Electron exe with ELECTRON_RUN_AS_NODE=1 → service-entry.cjs → existing coding-agent dist/web.js → main/startWebBootstrap → HTTP/SSE → existing web/`.

Development uses that same chain with `packages/coding-agent/src/web.ts` and the repository dev loader. Refresh for frontend changes; close/relaunch for backend changes. The browser launch scripts (`dev-web.cmd` and its helpers) have been removed: the desktop app is the way to use MyHarness, and `node --import ./scripts/dev-fast-loader.mjs ./packages/coding-agent/src/web.ts` runs the sources from a command line without opening a browser.

The source host anchors its working directory to the repository. The packaged host records that directory in `runtime.json` at build time, independently of where the executable is copied. This is intentional for this checkout's desktop/Web shared-data requirement: Agent configuration remains in `~/.myharness/agent` (or the existing environment override); current Session/Workspace data remains in the checkout's `data/`, not a new Electron data store. `MYHARNESS_DESKTOP_CWD` can explicitly select a different working directory; `MYHARNESS_DATA_ROOT` retains the backend's existing semantics. A different machine needs an explicitly chosen existing working directory; a build-time checkout path is not a universal installer data location.

Only Chromium host/third-party profile data is added under the Agent directory's `desktop-profile`. Third-party views use the separate persistent `myharness-third-party` partition, never the system browser profile. Web UI appearance preferences (theme, language, motion, widths, panel tab, run mode, notifications) are kept by the service in the Agent directory's `web-ui-prefs.json` and shared with the browser Web UI (see `packages/coding-agent/docs/web-ui.md`), so the per-start random port no longer resets them. Earlier desktop builds kept them only in the localStorage of each start's origin; on start, when the service has no shared preferences yet, `legacy-prefs.cjs` reads those copies from this profile's LocalStorage log (read-only) and moves the user's last choice of each preference there once. When copies exist but none can be read, the page starts with defaults and says so. Server settings and persisted conversations use the same backend paths.

The service listens on port 0 and reports the actual loopback address. A process waits for IPC before initializing, so the main process can first assign it to a Windows kill-on-close Job Object (Koffi calls Windows APIs). Descendant shells, PTYs and tasks inherit ownership. Window close requests existing graceful shutdown, waits up to eight seconds, then closes the job. The existing restart route retains its work checks and disposal, but desktop restarts are supervised over IPC rather than detached PowerShell. Single-instance locking activates the existing window.

Logs append to the existing data root's `logs/web-launch.out.log` and `web-launch.err.log`. Service/load failures produce a Chinese error page. No Agent data or credentials are copied into the distribution.

A click on the task-end notification is a Windows activation: it starts whatever the Start Menu shortcut carrying the app's AppUserModelId points at, which may be a new process rather than the running window. The id therefore has to name one launcher that starts this app. The packaged build keeps `MyHarness`; a source run of `electron.exe` uses `MyHarness.Dev`, because Electron always writes that shortcut without the app path and would otherwise compete for the installed app's notifications with a shortcut that starts Electron's default window. On start the packaged build also removes Start Menu shortcuts that still claim `MyHarness` without being able to start this app (a leftover of a source run, or a build folder whose executable is gone); Electron writes its own shortcut again before the next notification, and a shortcut of another installation that still exists is kept, because starting it forwards to the running window through the single-instance lock.

## Built-in browser and the workspace

The right-hand panel is one workspace with tabs: the four existing panels (Changes / Files / Terminal / Session) keep their single tab each, and any number of local files (text, code, Markdown, JSON, images, PDF, Office, audio, video) and websites can be open at the same time. The header's globe button opens a website tab. A tab strip at the top of the panel switches between them, closes one (× or middle click), closes the others (right-click menu), restores the most recently closed one, and reorders them by dragging; the open tabs and the active one are saved with the other page preferences, so they come back after a reload. Closing the panel keeps every tab; the panel's state is not thrown away when you close it.

Each website tab is a sandboxed `WebContentsView` without preload or Node integration: a real Chromium document with its own history, not an iframe or webview. Every tab shares one persistent `myharness-third-party` partition, so cookies, localStorage and (when the site stores its login there) login state survive restarts and tab switches; nothing is copied from or written to the system browser profile. Web links that open a new window become workspace tabs, downloads are saved with a collision-free name under the system Downloads folder and reported with progress (the host command surface can cancel by id and retry), and a toolbar shield lists site permissions. A permission request (camera, microphone, clipboard, notifications, geolocation, external open, …) is not granted by default: the tab asks with Allow for this session / Deny, an unanswered or abandoned request is denied, the decision is remembered for this app session only, and it can be revoked from the shield. The Agent cannot make that decision. This does not promise access to blocked networks or bypass site login, bot checks, DRM or Electron-specific site restrictions.

In-page find (`Ctrl+F` inside the page, the search button, or the Agent's `find` command) uses the real `findInPage`/`found-in-page` result and shows the match count. The file tabs have their own find bar for text files. The Agent can upload one workspace file into a page's `<input type=file>` with `upload`; the desktop host resolves the path inside the current workspace only, requires a regular file, enforces a 100 MiB limit and refuses directories, missing files and paths outside the workspace. Upload progress is not exposed by Chromium's file-input API, and a cancelled upload is a cancelled page-side operation, not a resumable transfer.

A native view is drawn above the whole page and takes no part in its layout, animations or stacking. `web/js/browser-view-sync.js` measures the tab's real box: while the box moves (panel drag, window resize, scrolling) the native bounds follow the measured box; a box that is hidden (animation, dialog, clipping, hidden page, inactive tab) is shown again only after two stable checks, and the view is also hidden while a dialog/popover/toast covers it, a scrolling ancestor clips it, the page is hidden, or the tab is not the active workspace tab. The page calls `hide` before rendering a non-browser tab, the component reports a null rectangle for its own tab when it unmounts, and active/tab/close state is enforced again in the host (`activate` without fresh bounds stays hidden, `close` never promotes another view to the old box). Main clamps bounds to the window and refreshes them on resize/maximize/restore/fullscreen events. Closing a tab cancels its downloads, clears its find/permission callbacks, timeouts and screenshot interval, detaches and closes the view, and drops its network references. The hidden page itself stays alive, so its history, form state and scroll position survive a switch; the fallback picture (`capturePage`, JPEG) is refreshed only while the view is visible. Load failure/45-second timeout leaves a visible message and a system-browser action. The context menu supports editing/copy and opening the page externally. No global keyboard shortcut or window-level fullscreen toggle is implemented. Multi-window OAuth flows are not implemented as a full browser product.

## The Agent's workspace tool

In Electron only, the service process gets a `workspace` tool (`packages/coding-agent/src/tools/workspace.ts`). It is registered only when `MYHARNESS_DESKTOP_HOST=1` and the IPC link is connected, so a plain CLI session never advertises it. Two channels, both request/response with a timeout and a real error on failure:

- **Browser channel** — the service asks the main process over the child-process IPC link; main acts on the addressed `WebContentsView` and answers with the state it reached: `list`, `open`, `ensure`, `activate`, `bounds`, `hide`, `refresh`, `close`, `state`, `navigate`, `back`, `forward`, `reload`, `stop`, `find`/`stopFind` (real match count and active match), `text`, `dom`, `ax` (Chrome accessibility tree), `interactive`, `click`/`type` (CSS selector or the index from `interactive`), `upload` (one workspace file into a page file input), `scroll`, `exec` (page JavaScript), `snapshot` (PNG), `downloads`/`download-cancel`/`download-retry`, `network` (recent request metadata: method, URL, status, type — no bodies or headers), `permission`/`permissions`/`revokePermission` for the session-scoped site-permission decisions, and `external` (system browser). Download and request logs are capped (50 and 200 entries) and never persisted. Only the app page can call these commands; the website itself never gets the bridge.
- **Workspace channel** — the page owns its tab list and the media elements, so main forwards the command to the page (`desktop:workspace`) and the page answers with the state it reached (`tabs`, `open`, `close`, `activate`, `closeOthers`, `move`, `reopen`, `media` with play/pause/seek/volume/mute/rate/subtitles). A page that does not answer in 15 seconds is an error, not an assumed success.

Both channels are reachable only from the app's own page (same service origin, main frame) through `contextBridge`; the page cannot call raw Electron or Node APIs. Screenshots are written to the session's temporary directory and returned by path instead of a multi-megabyte data URL in the model's context; the tool keeps the newest 50 workspace screenshots and deletes older ones.

## Verification limits

Use actual test reports for evidence. Unit tests and browser module smoke checks do not establish human input, visual alignment at every DPI level, all Git flows, clean-machine compatibility or login compatibility. The workspace and the built-in browser have: unit tests for the command surface, state machine and permission decisions (`test/browser-tabs.test.cjs` with a mocked Electron); a real-Chromium test of the page's tab model and workspace commands (`packages/coding-agent/test/web-workspace-tabs-browser.test.ts`); a real-Chromium test of native-view placement, hide-on-tab-switch, in-page find, upload validation and permission UI (`packages/coding-agent/test/web-workspace-browser-view.test.ts`); a real child-process IPC test of the Agent tool with an isolated faux model (`packages/coding-agent/test/workspace-tool-ipc.test.ts`); and a real-Electron harness (`test/electron-browser.e2e.cjs`) that drives the actual `WebContentsView` command surface, downloads, cancel/retry, popups, permission allow/deny/revoke, persistence across a restart, and runs the real `workspace` tool over real IPC against this Electron main process with a faux model. Run the harness twice with `node_modules/.bin/electron packages/desktop/test/electron-browser.e2e.cjs --phase=1|2 --profile=<dir> --downloads=<dir>`. That harness and the page fixture do not cover the app page's own transport (`contextBridge`/`ipcMain`/`desktop:status`); that path was exercised in this workspace with a one-off CDP driver against the running app at 100 %, 125 % and 150 % display scale, including a real pointer drag, Session/Terminal/file/media switches, maximize/restore while the browser was hidden, and tab close/reopen. That driver is not part of the repository, so its results are evidence for this machine only, not an automated guarantee. No real provider model turn was run; the tool round used the isolated faux model. Office documents remain read-only (download/external open), PDF uses Chromium's bundled viewer (view, zoom, page, search, copy, download), and image zoom/rotate is view-only (no crop, annotation or save). The app is unsigned; Windows SmartScreen policy may warn. No auto-updater or installer is provided by the directory target.
